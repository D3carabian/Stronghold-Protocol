# 后续自定义开发

## 已作出的决定

账号采用邮箱验证＋邀请码，Discord 可作为后续可选身份提供方。当前未配置邮件供应商，因此没有可用的邮箱
验证流程；部署入口暂由不同的 HTTP Basic 密码保护。不要将临时密码说成邀请码，也不要把发邮件写日志当验证。
邮件提供方、发件域名验证、DNS、限流和投递测试是下一阶段的外部输入。

未来用户角色为管理员、测试员、玩家、待批准用户；身份与游玩资格分开。短时单次验证码/链接、受限次数的
邀请码、服务器会话、撤销和审计都要实现。HTTP 和 WebSocket 同时鉴权，校验 Origin，并把游戏重连令牌绑定到
内部用户 ID。正式/测试环境使用独立 Cookie、密钥和 SQLite 数据库，不共享玩家真实数据。

## 分阶段交付

第一阶段是本次基础部署：fork、文档、两个受保护的实例、资源版本、构建验证、空闲发布与回滚。
第二阶段是邮箱与邀请认证和只读后台；配置邮件服务后再实现、测试真实投递并替换临时门禁。
第三阶段是持久战绩、可复现的 Bug 记录、观战和资源更新；数据库必须有独立备份和恢复演练。
第四阶段才是受规则约束的随机控制与玩法修复：每次干预经过游戏规则校验，在房间中明确标记并记录审计。
最后扩大自动化：上游正式版 → 合并候选 → 测试 → 测试服 → 验收 → 正式服空闲发布。

## 自动更新边界

现在可以运行 `python3 ops/prepare_update.py` 生成候选合并；它不会推送或部署，也不会强制覆盖冲突。
CI 检查随 push/PR 运行。没有启用定时拉取、后台自动合并或生产自动部署。
自动化的目标不是无条件跟随上游，冲突、测试失败、素材不全或正在对局时必须停止。
后续可以把候选创建接入 GitHub Actions，但不要让公开 PR 在生产服务器或存放 Windows 客户端的机器上执行。

## 测试与忠实还原

每个机制 Bug 保存来源证据和复现：代码、规则数据、素材版本、种子、初始阵容、玩家输入及管理员干预。
保留上游 golden 基线；修复导致的差异逐项解释，不因检查失败直接接受全部结果。
Safari 的模拟计算与桌面必须保持确定性，不在 `server/sim/` 使用平台相关随机数、时钟或近似 Math 函数。

## 预留环境变量（尚未使用）

后续认证模块会定义 `AUTH_PUBLIC_URL`、`AUTH_SESSION_SECRET`、`SMTP_HOST`、`SMTP_PORT`、`SMTP_USER`、
`SMTP_PASSWORD`、`MAIL_FROM`、`DATABASE_PATH`。这些只是接口设计，不是当前游戏已经识别的变量。
真实值放在服务器 `/etc/stronghold/` 的受限文件，不能进 Git、镜像或浏览器。
